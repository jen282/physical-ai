TeachArm 전처리 설계안 (SO-101 + LeRobot + ACT 기준)

조사 결과를 보면, 이 현장은 **"전처리를 많이 해야 하는 현장"이 아니라 "수집 조건을 고정하고 전처리를 최소화해야 하는 현장"**입니다. 리더-팔로워 방식, 단일 PC 시계, 30Hz 카메라와 30Hz 제어 주기 일치, LeRobot 포맷이라는 조건 덕분에 동기화와 궤적 품질은 기본적으로 양호합니다. 대신 진짜 위험 요소는 세 가지입니다. 물체 위치 변동이 큰데 에피소드는 50개뿐이라는 점, 노출/조명 정보가 비어 있다는 점, 그리고 추론 장치에 Raspberry Pi 5가 포함되어 있다는 점입니다. 아래 설계는 이 판단을 바탕으로 합니다.

1. 전처리 파이프라인 (실행 순서)
   단계 0. 원본 무결성 점검

기법: 에피소드별 프레임 수(parquet 행 수와 영상 프레임 수 일치), NaN/Inf 검사, 영상 디코딩 가능 여부, 관절값이 캘리브레이션 범위 안에 있는지 확인합니다.
근거: 8-1(LeRobot Dataset), 8-2(MP4). LeRobot은 녹화 중 중단되면 영상과 parquet 길이가 어긋난 에피소드가 남을 수 있습니다.
초기값: 영상 프레임 수와 parquet 행 수 차이 0 허용(1 이상이면 제외 후보).
순서가 바뀌면: 깨진 에피소드가 이후 통계 계산과 필터링 기준(중앙값 등)을 오염시킵니다.

단계 1. 동기화 검증 (보정이 아니라 측정)

기법: 타임스탬프 간격(dt) 분포 분석, action→state 상호상관으로 추종 지연 측정.
근거: 7-1(단일 PC 시계)이라 장치 간 시계 오프셋 보정은 불필요합니다. 하지만 LeRobot의 timestamp는 실제 측정 시각이 아니라 frame_index / fps로 기록되는 구조라서, 녹화 루프가 늦어지면 기록상으로는 33.3ms 간격이지만 실제로는 간격이 벌어집니다. 녹화 중 LeRobot 로그에 표시되는 루프 주기(dt) 경고를 반드시 확인해야 합니다. 또 USB UVC 카메라(3-2)는 일반적으로 내부 지연이 수십~100ms 수준이라 영상이 관절보다 1~3프레임 늦을 수 있습니다.
초기값: 실제 루프 주기가 50ms(1.5×공칭) 초과인 프레임 비율 5% 이상이면 에피소드 제외 후보. action→state 지연은 SO-101에서 통상 1~4프레임이 정상입니다.
판단 기준: 지연은 측정만 하고 데이터를 시프트하지 않는 것을 권합니다. 추론 때도 같은 카메라 지연이 그대로 존재하므로, 학습 데이터의 지연과 추론 환경의 지연이 일치하는 한 정책이 알아서 흡수합니다. 시프트 보정은 카메라 지연이 에피소드마다 들쑥날쑥할 때만 의미가 있습니다.
순서가 바뀌면: 동기화 문제를 모른 채 스무딩부터 하면, 어긋난 데이터를 매끄럽게 만들어 문제를 감추게 됩니다.

단계 2. 에피소드 필터링

기법: 메타데이터 기반 실패 에피소드 제외, 길이 이상치 제거(Robust z-score), 프레임 드랍 과다 에피소드 제외, 영상 품질 이상 에피소드 제외.
근거: 6-8(성공 여부 기록됨), 6-3(목표 50개). 데이터가 적어서 버릴 여유가 적으므로, 기준은 "명백히 나쁜 것만" 제거하는 보수적 방향으로 잡습니다.
초기값: 길이 Robust z-score > 3.5 제외, 실패 에피소드는 전부 제외. 재시도(Re-grasp) 후 성공한 에피소드는 제거하지 말고 태그만 붙이세요. 소량 데이터에서는 회복 동작이 오히려 정책의 강건성을 높일 수 있습니다. 다만 전체의 20%를 넘으면 정책이 망설이는 습관을 배울 수 있으니 비율을 확인합니다.
순서가 바뀌면: 정규화 통계를 먼저 계산하면 실패·이상 에피소드의 값이 평균/표준편차에 섞여 들어갑니다.

단계 3. 로봇 궤적 클리닝

기법: ① Hampel 필터(스파이크 제거) → ② (조건부) Savitzky-Golay 스무딩 → ③ 시작/끝 정지 구간 트리밍.
근거: 4-1(SO-101 저가 서보, STS3215 계열은 통신 오류 시 값이 순간적으로 튈 수 있음), 5-1(리더-팔로워는 입력 자체가 매끄러움), 4-3(연속값 그리퍼), 6-7(수동 리셋으로 인한 시작 정지 구간).
초기값:

Hampel: 반창(half window) 3프레임, 3σ. 스파이크만 국소 중앙값으로 치환하고 정상 신호는 건드리지 않습니다.
Savitzky-Golay: 창 5, 2차 다항식. 기본값은 꺼둔 상태를 권합니다. 리더-팔로워 데이터는 원래 매끄럽고, ACT의 액션 청크 + Temporal ensembling이 이미 스무딩 역할을 하기 때문입니다. 9-3에서 고주파 떨림이 확인될 때만 켭니다.
그리퍼 채널에는 스무딩 금지. 파지 순간의 급격한 닫힘 타이밍이 흐려지면 정책이 "천천히 쥐는" 동작을 배워 큐브를 놓칩니다.
트리밍: 관절 속도 노름이 임계값 이하인 상태가 15프레임(0.5초) 이상 지속되는 시작/끝 구간을 자르되, 움직임 시작 전 10프레임(약 0.33초)은 여유로 남깁니다.

중요한 주의점: 큐브를 쥐었을 때 리더 그리퍼는 더 닫히고 팔로워 그리퍼는 큐브에 막혀 덜 닫힙니다. 이 action-state 차이가 바로 "쥐는 힘"을 표현하는 정보이므로 오류로 간주해 보정하면 안 됩니다.
순서가 바뀌면: 스무딩을 Hampel보다 먼저 하면 스파이크 하나가 주변 5프레임으로 번집니다. 트리밍을 필터보다 먼저 하면 필터의 경계 효과가 동작 시작 부분에 걸립니다.

단계 4. (선택) 작업 단계 라벨링

기법: 그리퍼 위치 + 그리퍼 전류로 집기/이송/놓기 구간 자동 분할.
근거: 1-3(3단계), 4-4(전류 기록됨). 그리퍼가 닫히는 중 전류가 급상승하고 위치가 멈추는 지점이 "파지 성공" 시점입니다.
용도: ACT 학습 자체에는 필요 없습니다. 분석용으로, 정책이 실패할 때 어느 단계에서 실패하는지 진단하고, 단계별 시연 품질을 비교하는 데 씁니다. 전류는 처음부터 정책 입력에 넣지 말고, 기본 모델이 안정된 뒤 실험 변수로 추가하는 것을 권합니다.

단계 5. 영상 전처리 (결정적 처리)

기법: 디코딩 → RGB 변환 → 리사이즈 → 정규화.
근거: 3-3(640×480), 10-3(Raspberry Pi 5 추론), 1-5(일반 강체 큐브), 3-2(RGB만, 깊이 처리 불필요).
초기값: 320×240으로 다운스케일을 강력히 권합니다. ResNet18 백본의 연산량이 약 1/4로 줄어 Colab T4 학습 속도와 Pi 5 추론 모두에 결정적입니다. 상단 카메라 기준으로 큐브가 640×480에서 약 30px라면 320×240에서도 15px 정도로 위치 인식에 충분합니다. 가장 좋은 방법은 다음 수집부터 카메라 설정 자체를 320×240으로 녹화하는 것이고, 기존 데이터는 오프라인으로 리사이즈 후 재인코딩합니다.
하지 말아야 할 것: 왜곡 보정(Undistortion)은 생략합니다. 카메라가 견고하게 고정(3-8)되어 있고 엔드투엔드 정책이라 일관성만 유지되면 됩니다. 디노이징도 생략합니다. 추론 때 같은 처리를 매 프레임 실시간으로 해야 하는 부담만 생깁니다.
압축 관련: 학습 데이터는 AV1/H.264로 압축된 프레임이고, 추론 입력은 압축되지 않은 원본 프레임입니다. 이 차이가 작은 도메인 갭을 만들 수 있으니, 인코딩 품질(CRF)을 기본값보다 약간 높은 화질로 설정하는 것을 권합니다.
순서가 바뀌면: 증강을 리사이즈보다 먼저 하면 원본 해상도에서 증강 연산 비용이 4배가 되고, 크롭 비율의 의미도 달라집니다.

단계 6. 정규화

기법: 관절 상태/액션은 관절별 Mean-Std(Z-score), 영상은 LeRobot 기본 정규화.
근거: 4-2(6DOF), 4-5(관절 절대 위치).
핵심 원칙: 통계(stats.json)는 필터링과 트리밍이 끝난 학습 세트로만 다시 계산해야 합니다. 또한 SO-101의 캘리브레이션 파일이 수집 시점과 추론 시점에 반드시 동일해야 합니다. 캘리브레이션을 다시 하면 같은 자세라도 관절값이 달라져 정규화가 무의미해집니다. 이것이 저가 서보 팔에서 가장 흔한 "학습은 잘 됐는데 실전에서 안 움직이는" 원인입니다.
순서가 바뀌면: 정규화 후에 필터링하면 제외된 에피소드의 값이 통계에 남아 분포가 왜곡됩니다.

단계 7. 데이터 증강 (학습 중 온라인 적용)

근거: 1-6(위치 대폭 변동), 6-3(50개로 데이터 부족), 2-1/2-2(조명 정보 미기록으로 불확실성 존재).
초기값:

상단 카메라: Random shift(가장자리 4% 패딩 후 원래 크기로 랜덤 크롭) + ColorJitter(밝기 0.2, 대비 0.2, 채도 0.2, 색조 0.02).
손목 카메라: ColorJitter만 + 작은 회전(±5°). 손목 카메라는 그리퍼와의 상대 위치가 핵심 정보라 기하 변환을 약하게 합니다.
좌우 반전(Flip)은 금지입니다. 관절 좌표계와 영상의 공간 관계가 깨집니다.
LeRobot에서는 --dataset.image_transforms.enable=true로 켜고, 한 번에 적용할 변환 수는 2~3개로 시작합니다(옵션명은 사용 중인 LeRobot 버전에서 확인하세요).

주의: 증강은 위치 다양성 부족을 완전히 대체하지 못합니다. Random shift는 "물체가 화면에서 몇 픽셀 이동"을 흉내 낼 뿐, "로봇이 다른 관절 궤적으로 그 위치에 도달해야 함"이라는 액션 측 정보는 만들어내지 못합니다. 이 부분은 5번 항목의 재수집 계획으로 해결해야 합니다.

단계 8. 데이터 분할 및 포맷 변환

기법: 에피소드 단위 분할(프레임 단위 분할 금지), 물체 위치 구역별 층화 분할.
근거: 6-8(물체 위치 메타데이터 기록됨).
초기값: 50개 중 45개 학습, 5개 검증. 단, ACT의 검증 손실은 실제 성공률과 상관관계가 약하므로, 진짜 평가는 실물 로봇 테스트로 해야 합니다. 트리밍한 경우 LeRobot 데이터셋을 새로 만들어야 하므로(영상 재인코딩 포함) 원본은 반드시 별도로 보관합니다.

2. 비전 데이터 vs 로봇 데이터 처리 흐름

비전 쪽은 무결성 점검 → 품질 지표 산출(블러·밝기) → 리사이즈 → 정규화 → 증강 순서로 흐르고, 로봇 쪽은 무결성 점검 → 지연 측정 → Hampel → (조건부) 스무딩 → 트리밍 → 정규화 순서로 흐릅니다.

두 흐름이 만나는 동기화 지점은 세 군데입니다. 첫째, 단계 1에서 frame_index를 공통 키로 영상과 관절 데이터가 같은 시각에 묶여 있는지 확인합니다. 둘째, 단계 2에서 품질 판정은 각각 하되 제외 결정은 에피소드 단위로 함께 내립니다(영상만 나쁘고 관절은 괜찮아도 해당 에피소드 전체를 제외). 셋째, 단계 3의 트리밍 인덱스는 로봇 데이터의 속도로 계산하지만 동일한 인덱스를 두 카메라 영상에도 똑같이 적용해야 합니다. 이 세 번째 지점이 가장 실수가 많이 나는 곳입니다.

3. 학습 전용 vs 추론 공통 처리 구분
   구분 처리 항목
   학습 전용 (추론 때는 하지 않음) 에피소드 필터링, 트리밍, Hampel/스무딩, 단계 라벨링, 이미지 증강(Random shift, ColorJitter, 회전), 데이터 분할
   추론에도 동일 적용 필수 카메라 설정(해상도, 노출, 화이트밸런스, 초점 고정값), 리사이즈 크기와 보간 방식, RGB 채널 순서, 영상·관절 정규화 통계(같은 stats.json), SO-101 캘리브레이션 파일, 카메라 이름과 상단/손목 매핑 순서

추론에서 특히 주의할 점은 Raspberry Pi 5입니다. Pi 5에는 CUDA GPU가 없어서 ACT(ResNet18 × 2개 카메라 + Transformer)를 매 프레임 30Hz로 돌리는 것은 현실적으로 어렵습니다. 그래서 Pi 5에서는 Temporal ensembling을 끄고(매 스텝 추론이 필요하기 때문) 액션 청크를 한 번 예측한 뒤 n_action_steps만큼(예: 30~50스텝, 1~1.7초) 실행하는 방식으로 추론 빈도를 낮춰야 합니다. 노트북 GPU에서는 Temporal ensembling을 켠 버전과 비교하는 것을 권합니다.

4. 전처리로 해결하기 어려운 문제 (개선 우선순위)

1순위: 카메라 노출·화이트밸런스·초점 수동 고정. 3-5가 비어 있는데, USB UVC 카메라는 기본값이 대부분 자동입니다. 자동 노출 상태에서는 로봇팔이 화면에 들어올 때마다 밝기가 변하고, 에피소드마다 색감이 달라집니다. 이건 ColorJitter로 일부 흡수되지만 근본 해결은 v4l2-ctl로 수동 고정하는 것이고, 비용이 거의 들지 않아 가장 먼저 할 일입니다. 이미 수집한 데이터가 자동 노출이었다면 재수집을 권합니다.

2순위: 위치 다양성 대비 에피소드 수 부족. 큐브 위치가 "대폭 변동"인데 50개는 빠듯합니다. 작업 영역을 3×3 같은 격자 구역으로 나누고 구역당 최소 5~6개를 균등하게 채우는 계획적 수집이 필요합니다. 접시 위치까지 변한다면 조합이 늘어나므로 80~100개를 목표로 잡는 게 안전합니다. 증강으로는 액션 측 다양성을 만들 수 없습니다.

3순위: Pi 5 추론 성능 사전 검증. 학습 전에 Pi 5에서 더미 입력으로 ACT 1회 추론 시간을 먼저 측정하세요. 액션 청크를 실행하는 동안 다음 추론이 끝나지 않으면 로봇이 멈칫거립니다. 부족하면 입력 해상도 축소, ONNX 변환, 혹은 노트북 추론으로 역할을 조정해야 합니다.

4순위: 조명 고정. 2-1/2-2가 비어 있는데, 연구실 창가라면 시간대별 자연광 변화가 생깁니다. 블라인드를 치고 고정 LED를 쓰는 것이 증강보다 확실합니다.

5순위: 핸드트래킹 데이터 분리. 핸드트래킹(5-1 비교군)은 손 떨림과 리타게팅(IK) 오차 때문에 리더-팔로워와 데이터 분포가 다릅니다. 두 데이터셋을 절대 섞지 말고 별도 데이터셋으로 수집·학습해 비교하세요. 또한 핸드트래킹의 떨림 필터(One Euro 필터 등)는 오프라인 전처리가 아니라 조작 중 실시간으로 적용해야 합니다. 녹화된 액션은 실제로 로봇에 보낸 명령이어야 관측 영상과 인과관계가 맞기 때문입니다.

5. 전처리 검증 지표와 시각화

동기화: dt 분포 히스토그램(표준편차, 50ms 초과 비율), action→state 지연 프레임 수의 에피소드별 분포. 지연이 에피소드마다 일정하면 정상입니다.

궤적 품질: 관절별로 전체 에피소드를 겹쳐 그린 궤적 오버레이 플롯(이상한 에피소드가 눈에 바로 띔), 필터 전후 Jerk(가속도 변화율) RMS 비교, 필터 전후 RMSE(0.5° 이하여야 정상, 이보다 크면 필터가 신호를 깎고 있다는 뜻).

영상 품질: 에피소드별 Laplacian 분산(선명도)과 평균 밝기의 박스플롯. 박스가 에피소드마다 들쑥날쑥하면 자동 노출이 켜져 있다는 신호입니다. 증강 결과는 원본 1장 + 증강 8장의 격자 이미지로 육안 확인합니다(큐브가 화면 밖으로 잘려 나가면 안 됨).

데이터 분포: 물체 초기 위치 산점도(작업 영역 커버리지 맵, 빈 구역이 곧 재수집 대상), 에피소드 길이 히스토그램.

최종 지표: 결국 가장 중요한 것은 실물 로봇 성공률입니다. 학습 데이터에 있던 위치와 없던 위치를 구분해서 각 10회 이상 테스트하고, 단계별(집기/이송/놓기) 실패 지점을 기록하세요.

6. 추가 확인이 필요한 항목

판단을 정확히 하려면 다음이 필요합니다. 비어 있는 항목 중 영향이 큰 순서로 정리했습니다.

3-5 노출 설정, 2-1/2-2 조명: 증강 강도와 재수집 여부를 직접 결정합니다.
6-4 성공 비율, 6-5 이상 행동, 9-1/9-3 육안 품질: 필터링 기준을 얼마나 엄격하게 할지 결정합니다. 샘플 5개 재생 후 체크해 주세요.
6-1/6-2 시연자 수와 숙련도: 여러 명이면 시연자별 궤적 스타일 차이를 점검해야 합니다.
접시 위치의 변동 여부, 큐브 크기와 색, 작업면 색(2-5): 큐브와 작업면 색이 비슷하면 리사이즈 해상도를 다시 판단해야 합니다.
7-2 동기화 문제, 7-3 PC 부하: 녹화 중 LeRobot 루프 주기 경고가 나왔는지 확인해 주세요.
3-9 가림 현상: 상단 카메라에서 로봇팔이 큐브를 가리는 구간이 길면 손목 카메라 비중을 높이는 설계가 필요합니다.
사용 중인 LeRobot 버전(데이터셋 포맷 v2.1/v3.0 여부)과 Pi 5 vs 노트북의 정확한 역할 분담.
1-2 요구 정밀도: 접시 크기 대비 허용 오차를 알면 스무딩·해상도 판단이 더 정밀해집니다.
